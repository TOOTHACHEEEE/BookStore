## 一、项目介绍（建议背诵，控制在 1 分钟内）

**一句话版本：**
这是一个基于 **React + Ant Design + Vite** 的在线书店前端项目，6 个页面通过左侧菜单导航，书籍数据集中硬编码在 `Data.json` 中，购物车和搜索状态使用 **Context API** 全局管理，采用经典电商"左侧边栏 + 顶部 Header"布局。

**稍微展开版（如果被要求多说）：**
- **技术栈**：React 18 + React Router 6 + Ant Design 5 + Vite 5
- **页面**：书籍首页、书籍详情页、购物车、订单页、个人信息页、登录页
- **数据**：全部硬编码在 `src/data/Data.json`，方便后续接入后端时统一替换
- **状态管理**：`CartContext` 管购物车/订单/登录状态，`SearchContext` 管搜索关键词，避免 props 层层传递
- **布局**：`Layout.jsx` 作为公共骨架，左侧固定 Sider 放导航菜单，顶部 Header 放搜索框和用户信息，中间 Content 通过 `<Outlet />` 渲染子页面
- **存储**：购物车和订单数据用 `localStorage` 持久化，刷新页面不丢失

## 二、高频 CR 问题与建议回答

### 📌 A. 功能与页面相关

#### Q1：请介绍你的项目有哪些页面，分别做什么？
**建议回答：**
我的项目有 6 个页面：
1. **书籍首页**（`/`）：展示轮播图和书籍卡片列表，支持按书名/作者实时搜索过滤
2. **书籍详情页**（`/book/:id`）：展示单本书的详细信息，有"加入购物车"和"立即购买"按钮
3. **购物车**（`/cart`）：展示已添加的商品，可以删除商品、计算总价、结算生成订单
4. **订单页**（`/orders`）：展示历史订单列表，包含订单号、时间、商品明细和总额
5. **个人信息页**（`/profile`）：展示用户头像和基本信息表单，可以修改并保存
6. **登录页**（`/login`）：独立于主布局的登录页面，输入用户名即可登录

其中前 4 个是作业明确要求的核心页面，订单页和登录页是我为了完善电商场景额外补充的。

#### Q2：数据是怎么存放的？为什么这样设计？
**建议回答：**
所有数据都集中放在 `src/data/Data.json` 中，包括 `books` 数组和 `user` 对象。
这样做的好处是：
- **集中维护**：未来要接入真实后端时，只需替换这一处数据获取逻辑
- **前后端分离**：现在前端可以独立开发和演示，不受后端进度影响
- **符合作业要求**：题目明确建议"把数据集中存放在某处，例如 App.js 或 Data.json 中"

#### Q3：购物车功能具体是怎么实现的？
**建议回答：**
购物车的状态存在 `CartContext` 中，包含以下能力：
- **添加商品**：`addToCart`，如果同一本书已存在则数量 +1，否则新增一条记录
- **删除商品**：`removeFromCart`，通过 `cartItemId` 唯一标识删除
- **结算**：`checkout`，将购物车商品打包成一个订单，清空购物车
- **立即购买**：`buyNow`，不经过购物车直接生成订单

所有操作只在前端完成，没有调用后端接口。购物车和订单数据通过 `useEffect` 自动同步到 `localStorage`，刷新页面后数据不会丢失。

#### Q4：搜索功能是怎么跨组件工作的？
**建议回答：**
搜索框在顶部 `Header`（属于 `Layout` 组件），书籍列表在 `BookList` 页面，两个组件层级关系较远。
我使用 `SearchContext` 把搜索关键词提升到应用顶层，
- `Layout` 中的搜索框修改 `searchKeyword`
- `BookList` 读取 `searchKeyword` 并过滤书籍数组
这样避免了通过 props 层层传递，也符合 React 的"状态提升"原则。

#### Q5：登录状态是怎么保持的？
**建议回答：**
登录状态同样放在 `CartContext` 中统一管理。
- 登录成功后，`login()` 设置 `isLoggedIn = true` 并保存用户信息到 `localStorage`
- 页面刷新时，`useEffect` 从 `localStorage` 恢复登录状态
- 点击退出登录时，`logout()` 清除状态但不删除购物车和订单数据

登录页是一个独立路由（不在 `Layout` 的 `<Outlet>` 里），所以不显示左侧菜单，这是刻意设计的，模仿真实网站的登录体验。

### 📌 B. 设计原则相关（分值占比高，重点准备）

#### Q6：你是如何遵循 React 构件式开发原则的？
**建议回答：**
我把页面拆成了多个可复用的独立组件：
- **`BookCard`**：书籍卡片，在首页网格中复用，接收 `book` 和 `onAddToCart` 作为 props
- **`Layout`**：公共布局，包裹所有页面，包含侧边栏、Header、内容区
- **页面组件**：`BookList`、`BookDetail`、`Cart`、`Profile` 等负责各自的业务逻辑

这样做的好处是：
- **职责单一**：每个组件只做一件事
- **可复用**：`BookCard` 可以在任何需要展示书籍的地方复用
- **易维护**：修改一处不会影响其他组件

#### Q7：你为什么用 React Router 的 Outlet？路由是怎么配置的？
**建议回答：**
路由配置在 `App.jsx` 中，使用嵌套路由：

```jsx
<Route path="/" element={<AppLayout />}>
  <Route index element={<BookList />} />
  <Route path="book/:id" element={<BookDetail />} />
  <Route path="cart" element={<Cart />} />
  <Route path="orders" element={<Orders />} />
  <Route path="profile" element={<Profile />} />
</Route>
<Route path="/login" element={<Login />} />
```

`AppLayout` 作为父路由，内部用 `<Outlet />` 渲染子页面。这样所有需要侧边栏的页面共享同一个 `Layout`，而登录页作为独立路由不进入 `Layout`，从而实现不同的布局需求。

#### Q8：你为什么选择 Ant Design？用了哪些组件？
**建议回答：**
选择 Ant Design 是因为：
- 它是企业级 React UI 库，组件丰富、文档完善
- 视觉风格统一，适合电商后台/管理系统类项目
- 支持主题定制，我通过 `ConfigProvider` 设置了主色调为 `#1890ff`

用到的主要组件：
- **布局类**：`Layout`、`Sider`、`Header`、`Content`
- **导航类**：`Menu`、`Dropdown`
- **数据展示类**：`Card`、`List`、`Table`、`Descriptions`、`Carousel`
- **表单类**：`Form`、`Input`、`Input.Search`
- **反馈类**：`Button`、`Badge`、`Tag`、`message`、`Empty`

#### Q9：你的工程结构是怎么分层的？为什么这样分？
**建议回答：**
```
src/
  components/    # 可复用的通用组件（BookCard、Layout）
  pages/         # 页面级组件，每个对应一个路由
  context/       # 全局状态管理（CartContext、SearchContext）
  data/          # 静态数据（Data.json）
  utils/         # 工具函数（价格解析、总价计算）
  App.jsx        # 根组件，配置路由和 Provider
  main.jsx       # 入口文件
```

分层理由：
- **components vs pages**：components 是可复用的"积木"，pages 是具体的"页面"，职责清晰
- **context 独立出来**：状态逻辑集中管理，避免散落在各个组件里
- **utils 独立出来**：价格解析这类纯函数逻辑可以复用，也方便写单元测试
- **data 独立出来**：未来替换为 API 请求时，改动范围最小

#### Q10：为什么把 Context 分成 CartContext 和 SearchContext 两个，而不是放一个？
**建议回答：**
这是为了遵循"单一职责原则"和性能考虑：
- `CartContext` 管理购物车、订单、登录这三类相关的用户状态
- `SearchContext` 只管理搜索关键词，逻辑非常简单

如果合并成一个巨大的 Context，任何一个小状态变化都会导致所有消费该 Context 的组件重新渲染。分开后，修改搜索关键词不会触发购物车相关组件的重新渲染，性能更好，逻辑也更清晰。

#### Q12：AI 生成的代码你有没有修改过？举个例子。

### 📌 D. 可能的追问/挖坑题（提前想好说法）

#### Q14：你作业要求说"4 个页面"，你为什么做了 6 个？
**建议回答：**
作业确实要求主页、书籍详情、购物车、个人信息这 4 个核心页面，我都做了。额外增加的登录页和订单页是为了让电商流程更完整（浏览 → 加购/购买 → 查看订单 → 登录账号），属于锦上添花。如果老师觉得不合适，我可以只展示核心 4 个页面。

#### Q15：作业要求"不对按钮点击动作做出响应"，为什么你的"加入购物车"有反应？
**建议回答：**
我理解题目的意思是"不需要调用后端 API，不需要真正的后端交互"。所以我做的所有按钮点击都是纯前端响应：
- "加入购物车" → 只修改前端的 `cart` 状态，弹出一个 `message.success` 提示，没有发送任何 HTTP 请求
- "立即购买" → 同样只生成前端订单，不调用支付接口
- "保存个人信息" → 只弹出保存成功提示，没有 POST 到服务器

所有交互都局限在浏览器端，符合"暂时不做后端访问处理"的要求。

#### Q16：你的价格为什么用 `$` 符号而不是 `¥`？
**建议回答（提前想好，这可能是小细节但老师会注意到）：**
这是一个可以改进的点。初始数据里用了 `$`，后续如果要完善，可以在 `utils/price.js` 中统一处理货币符号，或者把数据中的价格改为人民币格式。当前主要是为了演示价格解析和计算逻辑。

#### Q17：如果以后真的要接后端，你打算怎么改？
**建议回答：**
- **数据层**：把 `import data from '../data/Data.json'` 替换成 `fetch` 或 `axios` 请求
- **状态层**：`CartContext` 中的 `addToCart`、`checkout` 等方法内部调用 API，成功后再更新本地状态
- **用户认证**：登录时调用后端接口获取 JWT Token，用 `http-only cookie` 或 `localStorage` 存储
- **工程结构**：可以在 `src/services/` 或 `src/api/` 目录下封装所有 API 请求函数

由于数据已经集中存放，替换成本很低。

#### Q18：`useEffect` 里读取 localStorage 为什么放在 `CartContext` 而不是 App.jsx？
**建议回答：**
因为 `localStorage` 里存的是业务数据（购物车、订单、登录状态），这些数据属于 `CartContext` 的职责范围。把它放在 Context 内部，可以让 `App.jsx` 保持简洁，只负责路由配置。这也符合"关注点分离"的原则。

#### Q19：`parsePrice` 工具函数存在的意义是什么？
**建议回答：**
数据中的价格是字符串（如 `"$49.90"`），计算总价时需要先转成数字。我把这个解析逻辑抽到 `utils/price.js` 中，好处是：
- 避免在多个组件里写重复的 `replace('$', '')`
- 如果以后价格格式变了（比如加上 `¥` 或千分位逗号），只需要改这一个函数
- 纯函数逻辑方便写单元测试
